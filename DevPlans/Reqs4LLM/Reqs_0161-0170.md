### 缺陷一：`leadingOverlapCount` 的 `prefix(while:)` 對「多讀音桶」誤判 k 值

`applyFuriousFrontCandidate` 的首段重合路徑（P165）以
`candidate.keyArray.prefix(candidate.keyArray.count - 1).prefix(while: { lastKey.allValues.contains($0) })`
數「開頭連續重合段數」k。若組字器尾鍵是**多讀音桶**（如聲調桶 [ㄊㄚ,ㄊㄚˊ,ㄊㄚˇ,ㄊㄚˋ,ㄊㄚ˙]），
且候選的前兩段恰好都 ∈ 該桶（如候選 [ㄊㄚ,ㄊㄚˊ,ㄇㄚ] 類、或狂拼容錯展開下的同音異調
候選），`prefix(while:)` 會把 k 數到 2——但 `dropFirst(k)` 之後覆寫 span 仍以
`anchor-1` 起算 `candidate.keyArray.count` 段，**覆寫 span 與實際插入的鍵數錯位**，
導致覆寫失敗或誤覆寫相鄰內容（潛在重複字元）。

### 缺陷二：三路徑皆不命中時，else 插入完整 keyArray 造成讀音重疊

`applyFuriousFrontCandidate` 的四路徑判定（置頂無橫跨／跨邊界／首段重合／前方單音節）
在「候選段數 > 組字器鍵數＋注拼槽可承接鍵數」時，若置頂無橫跨、跨邊界（鍵數不足）、
首段重合（首段不 ∈ 尾鍵桶）皆不成立，落入 else **插入完整 keyArray**——
如組字器 [ㄇㄚ桶]（嗎）+ POM 建議「他媽的」（[ㄊㄚ,ㄇㄚ,ㄉㄜ˙]）時，
插入後組字器變 [ㄇㄚ桶, ㄊㄚ, ㄇㄚ, ㄉㄜ˙]，組句「嗎他媽的」——**重複的「ㄇㄚ」
鍵與組字器既有鍵重疊**。IH150 的「tama」場景（組字器 1 鍵、候選首段恰為尾鍵）由
首段重合接住，但「首段不重合」的變體漏網。

### 缺陷三：`fetchPOMSuggestion` 的 `alternateKeys` 容錯匹配過寬，撈出段數溢出的 POM 建議

實測確認（2026-08-31）：`tama` 時 copilot walk 組句 `[他媽]`（keyGen.ngramKey =
`()&()&(ㄊㄚ-ㄇㄚ,他媽)`、head 2 段），但 `fetchPOMSuggestion` 經 `alternateKeys` 撈回
stored key `()&(ㄋㄧˇ,你)&(ㄊㄚ-ㄇㄚ-ㄉㄜ˙,他媽的)`（head 3 段）——因 `matchesPrimaryHead`
只要求 stored head 含 query head 的任一 primary 段，且「單段候選 vs 多段原始」的拒絕特例
**反向不成立**（query 2 段、stored 3 段時不攔截）。於是 copilot 窗出現 3 段「他媽的」，
與組字器實際鍵數（2）脫節——就地選中後即觸發缺陷二。P165 的置頂段去重（IH151）只處理
「同 value 重複」，不處理「keyArray 段數與組字器鍵數不符」。

## 手術內容

### 修復一：`leadingOverlapCount` 只允許「單一尾鍵承接且 k 恆為 1」

首段重合語義應為「**僅候選首段**與組字器尾鍵重合」（單一音節桶承接單一讀音段），
不應對多讀音桶做連續前綴數算。改法：
- `leadingOverlapCount` 改為布林式判定：僅當 `candidate.keyArray.count >= 2`、
  候選**首段** ∈ 組字器尾鍵桶、且**第二段不 ∈ 尾鍵桶**（或直接只取 k = 1）時生效；
- 保留「重合讀音全部落於最後一鍵」的幾何前提（P165 註解不變），但 k 恆為 1——
  消除 `prefix(while:)` 連續數算的錯位風險。

### 修復二：三路徑皆不命中時，不再插入完整 keyArray——改為「尾鍵承接」收斂

當置頂無橫跨／跨邊界／首段重合皆不成立、且候選段數大於組字器可承接鍵數時，
**禁止插入完整 keyArray**。改法：
- 若候選**首段** ∈ 組字器尾鍵桶（但第二段不重合，即首段重合不成立的原因只是
  `candidate.keyArray.count < 2` 或第二段外移）——仍走「只插首段之後」的語義；
- 否則（首段不 ∈ 尾鍵桶）：**靜默退回（`.failed`）**，不更動組字器——
  避免「嗎他媽的」類讀音重疊；呼叫端（`confirmFuriousFrontCandidate`）已有
  `romajiBackup` 復原邏輯承接。
- 邊界：候選段數 ≤ 組字器鍵數＋1（注拼槽）時維持既有 else 語義（正常逐讀音單鍵插入）。

### 修復三：`alternateKeys` 攔截「stored head 段數 > query head 段數」的建議

`LXPerceptor.alternateKeys` 的 `acceptMatch` 判定增加段數上限防線：
- stored head 段數 **大於** query head 段數時拒絕（`candidateSegmentCount > originalSegmentCount`
  即 skip）——使 `fetchPOMSuggestion` 不再撈回「比當前讀音更長」的記憶；
- 維持既有語義：段數相等（容錯去聲調）與段數更短（short→long 的既有使用情境）
  照常接受。
- 注意：此修復可能影響既有 POM 測試（如「tamade」時 copilot 3 鍵、stored「他媽的」3 段
  段數相等、不受影響；「tama」時 copilot 2 鍵、stored 3 段 → 不再撈出——IH150 的
  置頂 POM 建議因此改變，測試需同步更新以反映「段數溢出建議不再出現」的新語義）。
