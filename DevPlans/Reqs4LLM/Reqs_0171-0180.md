## 要解決的問題

使用者回報：狂拼（Furious）模式副駕（copilot）選字窗的**單漢字候選似乎沒有按照
頻率排序**。例：敲「wo」時，「喔（ㄨㄛ）」出現在最前列、而「我（ㄨㄛˇ）」等
ㄨㄛˇ 讀音的漢字需要滑鼠滾輪翻頁才能看到——明明「我」的實際權重更大。

**調查過程（實機資料探針）**：以真實 factory 辭典
（`VanguardFactoryDict4Typing.txtMap`，本機 BuildToolPlugin 產出）載入後直接查詢
「wo」的聲調桶 `[.multipleKeys(["ㄨㄛ","ㄨㄛˊ","ㄨㄛˇ","ㄨㄛˋ","ㄨㄛ˙"])]`，
實測權重：`我（ㄨㄛˇ）=-5.043`（真實高頻）、`喔（ㄨㄛ）=-5.183`、
而**另有一條無調墊底條目 `我（ㄨㄛ）=-9.465`**（count=0 墊底低頻字權重，
`weighten` 的 `case 0` 分支產出；該「聲調專屬」與「無調 fallback」雙鍵結構
為 Vanguard Lexicon 資料本身所帶——Vanguard Lexicon 編譯成 mcbopomofo 格式的
sorted TSV 供閱讀分析，執行期由 VanguardTrie 依自身規則解讀同一批
precompiled weight）。探針結果：修復前桶查詢回傳的「我」以 **ㄨㄛ（無調、
-9.465）** 形態出現於索引 22——排在「喔」之後極遠處，與使用者症狀完全吻合。

**根因**（程式碼盤點定位）：`unigramsForWithAlternatives` 的
`factoryChoppedUnigramsFor`（「&」連讀查詢）依 trie 鍵序（無調「ㄨㄛ」先於
聲調「ㄨㄛˇ」）回傳條目；下游 `rawAllUnigrams.consolidate(filter:)` 的
「先插入者勝」去重（`HomaCompatShims.swift`，於 `sort` **之前**執行）
把同詞值「我」的第二條（高權重 ㄨㄛˇ）丟掉、保留無調低權重條目——
桶查詢（multipleKeys，狂拼注拼槽展開的 copilot 窗候選來源）中「我」便以墊底
權重下沉。該缺陷僅在「同詞值跨多讀音鍵」的桶查詢下浮現；單鍵 fast path
（`unigramsFor(keyArray: [String])`）無跨鍵重複、不受影響。

## 手術內容

`factoryChoppedUnigramsFor(keyArray:entryType:partiallyMatch:)` 在組裝完 grams 之後、
回傳之前，新增「同詞值去重、保留最高機率者」：

- 以 `[String: Homa.Gram]` 依 `current`（詞值）收集，機率更高者覆蓋既有者；
- 空詞值條目跳過；
- 回傳 `Array(bestByValue.values)`（迭代順序不影響——呼叫端
  `unigramsForWithAlternatives` 最終仍以 `sort { $0.probability > $1.probability }`
  排序，`abbreviatedWordCandidates`（R2-α）亦先排序再去重）。

**範圍收斂**：此去重僅限原廠辭典查詢內部（factory「&」連讀路徑），
使用者片語／磁帶的「先插入者勝」覆蓋語義（`allUserPhraseUnigrams + rawAllUnigrams`
前插、cassette `insert(at: 0)`）完全不受影響——不做全域 consolidate 語義變更，
不觸碰 fast path（單鍵查詢無跨鍵重複，本就無此缺陷）。Homa 零改動。

## 要處理的事務

1. AppKit 版安裝程式會在安裝程式之後循環彈出「安裝成功」的訊息。在 macOS 15 / 26 / 27 系統下倒是不影響安裝程式的自主結束，但在 macOS 10.13 High Sierra 系統下測試發現這個問題會逼得使用者使用 `killall` 或 `kill -9` 才能關掉安裝程式。

2. SwiftUI 版偏好設定畫面會在當前的安裝程式 view 的基礎上多出背景 color mesh、以更大的 window size 呈現這個 color mesh。你看是否可以移植給 AppKit 版安裝程式。手術時安裝程式 main window size 就跟隨 SwiftUI 版安裝程式的 Window Size 好了，且 mesh 的左上角也用相同的 font size & style 顯示相同的文字。

## Phase 173 實作結果（2026-08-31，兩倉）

> AppKit 版安裝程式（`CtlAppInstaller4Cocoa`／`VwrAppInstaller4Cocoa`）修復「安裝成功」
> 提示循環彈出（macOS 10.13 High Sierra 上會迫使使用者以 `killall` 強制關閉），並將
> SwiftUI 版安裝程式的背景 color mesh（含左上角標題文字、主視窗 1000×630 content size）
> 移植至 AppKit 版。**Homa 零改動**；改動面：AppKit 安裝程式兩檔（controller＋view），
> 兩倉鏡像。

**背景一（循環彈窗根因）**：先前「AppInstaller // Refactor the management of
alerts」的改動把 Cocoa 前端的警示管理統一收斂到 `alertItem` 之後，`refreshUI()` 會在
`alertItem == nil` 時把 `currentAlertContent`（如 `.postInstallOK`）轉換成
`alertItem` 顯示；但**轉換後從未把 `currentAlertContent` 歸零**——使用者在 sheet 上
按 OK 後，completion 先 `alertItem = nil`（觸發 `config.didSet` → 再次 `refreshUI`），
`currentAlertContent` 仍是 `.postInstallOK`，於是被再次重建並彈出新的「安裝成功」
sheet。現代 macOS 上 `terminateWithDelay()` 仍能在 0.1 秒後讓程式退出，因此只是
閃過重複提示；但 macOS 10.13 上 `NSApp.terminate` 遇上未結束的 modal sheet 會
被延後，而每輪 runloop 又彈出新的 sheet，形成無法結束的無限循環。SwiftUI 版不受
影響：`alert(item:)` 關閉時會自動把 binding 寫回 nil，且 `onChange(of:
currentAlertContent)` 不會對同一值重複觸發。

**修復一**：Cocoa 版 `refreshUI()` 在把 `currentAlertContent` 轉換成 `alertItem` 的
同時，立即把 `currentAlertContent` 設回 `.nothing`（「消耗掉」）——alert 關閉後
`refreshUI` 再被觸發也不會重建同一個警示；此邏輯只在 Cocoa 前端的 `refreshUI()`
內執行（SwiftUI 前端的 `updateAlertItemFromConfig()` 不更動，避免破壞
`onChange` 驅動）。

**背景二（color mesh 移植）**：SwiftUI 版安裝程式（`InstallerApp4SwiftUI`＋
`VwrAppInstaller4SwiftUI` 的 `GradientViewWrapper`）以 2×2 四角色 mesh
（左上橙 0.93/0.49/0.21、右上綠 0.31/0.73/0.30、左下藍 0.38/0.58/0.81、
右下黃 0.97/0.84/0.02；macOS 15+ 用 `MeshGradient`，其餘以 64×64 方格在
**線性色域做雙線性插值、再轉回 sRGB** 的 Canvas fallback），在 1000×630 的
content size 主視窗內墊底，左上角以 30pt 斜體粗體白色文字（黑色硬陰影
offset 5,5）顯示「i18n:Installer.VChewingInputMethod」，安裝程式內容以
圓角卡片＋黑色 radius-3 陰影置中疊於 mesh 之上。

**修復二（AppKit 移植）**：
- `VwrAppInstaller4Cocoa` 新增 `public static let meshWindowWidth = 1_000`／
  `meshWindowHeight = 630`（與 SwiftUI 版 Window Size 一致）；`loadView()` 改為
  組裝 container：`MeshGradientView`（新私有 NSView 子類，以 CoreGraphics 逐格
  繪製與 SwiftUI Canvas fallback 完全相同的線性色域雙線性插值 mesh，`isFlipped`
  座標系使四角色方位一致）`pinEdges` 填滿、左上角 `NSTextField` 標題
  （30pt 斜體粗體 descriptor、白色，陰影以 attributed-string `.shadow`
  屬性繪製——offset 5,-5、硬陰影，方向與 SwiftUI 版一致）、中央置中的
  `InstallerCardView`（新私有 NSView 子類，以 `draw(_:)` 直接繪製：
  frame 四周預留 16pt margin 讓外框留在 bounds 內；
  thick round-rectangle outline：以比可見卡片大 10pt 的圓角矩形繪出，外框
  基色為 `makeOutlineColor()`（依底色 brightness 門檻：亮底→純白、暗底→
  純黑），再以 `controlBackgroundColor` 覆蓋為實心色（皆 dynamic color、
  隨外觀自動變化），邊緣以 NSShadow（系統 `shadowColor`@0.3、blur 3）
  模糊柔化；底色 `underPageBackgroundColor`）、既有 `body` stack 以
  寬度 533 約束置於卡片內（上方加 20pt inner padding，對應 SwiftUI 版
  GroupBox 的頂部留白）。
- `CtlAppInstaller4Cocoa`：`init` 的 `contentRect` 改為 1000×630；
  `windowDidLoad4Mavericks`／`windowDidLoadSinceYosemite` 的
  `setFrame(fittingSize)` 改為 `setContentSize(1000×630)`（content size 精確
  對齊 SwiftUI 版 `w.setContentSize`，避免「frame 含標題列 → content 縮水 →
  與 container 高度約束衝突」）。

**事主複驗修正（依 SwiftUI 版表現逐項調整）**：① 標題文字陰影改以 attributed-string
`.shadow` 屬性繪製（原 layer 陰影方向與 SwiftUI 版不一致）；② 卡片內容補上頂部
inner padding；③ 卡片外框改為 draw-based（`draw(_:)` 輸出會被裁切到視圖 bounds，
原 layer 陰影不可見）；④ **pin 約束正負號修正**：內容釘住「可見卡片」四邊時，
trailing／bottom 須用負號（先前 +16 把內容往右下推、溢出卡片右/下緣）；⑤ **外框
顏色**：`makeOutlineColor()` 取 `windowBackgroundColor` 的 HSB brightness，超過
0.5 門檻→純白（brightness 1.0）、否則→純黑（0.0）——brightness-only、hue／
saturation 不變——再以 `controlBackgroundColor` 覆蓋為外框實心色（light 純白

### 根因

macOS ≤10.12 的輸入法程序直接呼叫 ComDlg32（NSOpenPanel／NSSavePanel）會使輸入法與當下客體 app 陷入無限風火輪死迴圈（既有 `InfoMessage.TechnicalReasonNSOpenPanel` 文案已載明死迴圈與硬重啟風險）；macOS 10.13+ 無此問題，故偏好設定中會開面板的按鈕一律要求「≤10.12 不呼叫面板、以替代交互處理」。全量盤點 SettingsCocoa 六處 ComDlg32 入口：
