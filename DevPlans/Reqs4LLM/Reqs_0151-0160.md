## 要解決的問題

### M1：打字模式枚舉化（取代布林組合與散落閘門）

- 現況：`prefs.furiousTypingEnabled` 布林＋`prefs.cassetteEnabled` 布林＋`composer.isPinyinMode`
  的隱式組合散落於 `isFuriousTypingModeEffective`／`hasFuriousTailPending`／
  `isFuriousCopilotCandidateWindowVisible`（P150 第六波已抽象）與 `handleComposition` 分派
  （`InputHandler_HandleComposition.swift:20-35`，仍吃 `cassetteEnabled` 布林）。
- 目標：引入明確的打字模式枚舉（如 `enum TypingMode { .cassette, .bopomofoKeyblock, .pinyinKeyblock, .pinyinFuriousTyping }`），
  `handleComposition` 分派與閘門 API 改吃枚舉；`furiousTypingEnabled` pref 語義併入枚舉後決定去留
  （可保留為「快速切換」快捷開關、或改由枚舉直接承載）。
- 注意：磁帶與注拼（含狂拼）互斥語義、SCPC 守衛（狂拼完全無效）須在枚舉化後維持不變；
  `TypingMethod` enum（`vChewingFactory/codePoint/haninKeyboardSymbol/romanNumerals`）為另一層
  既有概念，勿混淆、勿併入。

### M2：讀音鍵 helper 統一（消除重複實作）

- 現況：兩套並存的「無調讀音→聲調候選桶」展開邏輯——`makeToneInsensitivePinyinQueryKey`
  （`Typewriter_BPMFFullMatch.swift:180`）與 `furiousToneInsensitiveBucket`
  （`InputHandler_FuriousResegmentation.swift:173`）語義一致（同以 `allowedIntonations` 展開）、
  實作寫法略有差異（前者 `forEach`＋去重守衛、後者 `map`），日後可能漂移。
- 目標：抽成單一共用 helper（建議放 Tekkon 或 Typewriter 共用層），兩處呼叫端改接；
  行為逐字節保持不變（既有 IH116–125 測試全數維持通過）。
- 若發現兩者存在細微語義差異，以「狂拼自動 chop 展開」為準並在語義差異記錄中註明。

### M4：Homa 組字器重切 API（評估原子化）

- 現況：P150 方案 B 的重切用「scratch 副本 `dropKey` 迴圈＋`insertKeys` 試算、勝出後對真組字器
  重做同樣 drop+insert」，無單一原子 API；每次候選試算都複製整個 assembler。
- 目標：評估並（若合理）新增 `replaceKeys(from:with:)` 一類原子重寫 API（沿用 Phase 134/136 的
  座標化寫回紀律：游標、覆寫狀態、POM 一致性）；或證實現有「drop+insert」組合已足夠、記為
  「不施工」並寫明理由。
- 注意：此 API 是「跨音節數重切」（`xian`→`xi'an` 類，P150 後續）的前置；若本 Phase 評估為
  不施工，跨音節數重切維持後續。

### M6：鍵盤佈局翻譯旗子

- 現況：`InputSession_HandleEvent.swift:173` 的鍵盤佈局翻譯條件依賴 `isComposerUsingPinyin`
  （＝`composer.isPinyinMode`）；狂拼要求拼音故現況可運作，但狂拼模式沒有顯式旗子。
- 目標：狂拼模式（或枚舉化後的對應枚舉值）在該條件中顯式列明，避免「閘門語義與佈局翻譯條件
  脫鉤」的隱式依賴（現況靠 `isComposerUsingPinyin` 間接涵蓋）；純旗子補強、無行為變更。

### M4：Homa 重切 API 評估（不施工＋理由）

- 結論：**記為不施工**。理由：
  1. 現有「scratch 副本 drop+insert 試算、勝出後對真組字器重做 drop+insert＋失敗防禦回滾」組合
     已正確涵蓋失敗路徑；組字器同執行緒同步使用、試算都在 scratch 上進行，真組字器的 drop+insert
     是整段流程的最後一步、中間態無外部觀察窗口。
  2. 原子 `replaceKeys(from:with:)` 的真正動機是「跨音節數重切（`xian`→`xi'an` 類）」的前置；
     該項目已明確延後另立 Phase，屆時再與 Phase 134/136 座標化寫回紀律（游標、覆寫狀態、POM
     一致性）一併設計，避免現在為假設性需求改動 Homa 核心模組（LGPL、需同步 Legacy 鏡像＋測試）。
  3. 本 Phase 零 Homa 變更，Homa 54/54 維持。
- 註：`furiousTrail` 存續本身就是 trail span 無 explicit override 的保證；trail 自癒不變量檢查
  （長度、尾鍵桶逐一比對）已把「drop 不完／插入失敗」的所有可觀測副作用壓在真組字器改動之前。

#### Homa 候選排序修正（2026-08-27，P148→P151 期間 macOS 側 Homa 更動一併同步）

事主 2026-08-27 報告：讀音插入組字器後叫出選字窗，「細按」排最前、壓過高分「西岸」

- **根因（fetchCandidates 排序鍵順序錯誤）**：`Homa_CandidateAPIs_FetchAndApply.swift`

  節點」（pair 相等含 keyArray＋value 完整比較）判定成功。

> 研究結論與後續 Phase 規劃（S1／S2／S3）詳見該報告；以下為摘要。

### 核心發現

1. **方向一（POM optional 容錯查詢 API）——可行、且為後續一切的解鎖前題**：POM 目前只有 exact-match
   ngramKey 查詢＋`alternateKeys` 等值/後綴比對兩級；Furious 聲調桶（`makeToneInsensitiveVariants` 首位
   ＝無調形）與不完整讀音使兩級皆落空（「完全查不到」）。建議引入 tone-insensitive prefix 查詢模式
   （三位置讀音去聲調＋前綴比對、values 維持 exact），成本與既有 `alternateKeys` 全掃描同級（容量
   ≤500）；此 API 亦為 P151 待決 T1（copilot 組句套用 POM，設計已定稿）的啟用前題。
2. **方向二（POM 資料作 n-gram 來源）——資料就緒、注入點明確**：POM 的 ngramKey 天生三層結構
   （anterior&previous&head），perception 帶 count/timestamp，天然是 bigram/trigram 語料；注入點＝
   `LMInstantiator.unigramsFor`；Homa 選字窗既有「排除帶 previous 的 grams」機制（
   `Homa_CandidateAPIs_FetchAndApply.swift:40`）→ POM 衍生 bigram 不污染候選窗。需補外源開關
   （UserDef＋Config＋syncPrefs＋l10n）、unigramsFor 快取指紋納入 POM 世代、分數映射取捨
   （新鮮記憶 ≈ −0.171 對比詞典 −0.x～−11，需防過度支配）。
3. **方向三（Homa trigram）——引擎端代價遠低於直覺、但資料才是真問題**：DP 已是 1D、bigram 本就採
   「最佳路徑前驅」近似（`Homa_PathFinder.swift:74-76`），trigram 只要再往回多看一跳
   （`parent[i - parent[i].segLength]`）、**DP 結構零改動**。但實測 factory 詞典（
   `VanguardFactoryDict4Typing.txtMap` 442,105 行）**無任何 ≥4 欄列（bigram 資料零筆）**、且
   LMAssembly 的 `makeFactoryUnigrams` 兩處把 trie 的 `previous` 欄直接丟棄——**bigram 鏈路在生產環境
   為三重休眠**（引擎備好、資料缺席、轉換層斷鏈）。trigram 若無語料就是第二條休眠鏈路；唯一現成的
   trigram 語料正是 POM 本身。
4. **方向四（DAG-DP 自動選取 vs override 錨定）——文書整理完成**：引擎端 n-gram 走
   `Node.getScore(previous:)` → `.withTopGramScore` 自動覆寫（軟性、路徑可逆、`isExplicitlyOverridden`
   不置 true），對照 POM 建議 API 的 `.withSpecified` 硬錨定（顯式選字）；兩者互補，前者即 DevReq 所述
   「更強靈活性」的來源。
5. **方向五（DevReq 追加：Typewriter 層「套用 POM 記憶」的部分可省略性）——部分紅利、非全額**：S2／S3
   落地後，「自動段」（solidify 後自動 apply、候選窗自動置頂）可交由 n-gram 體系承擔，刪掉 4 次
   retokenization 重試／`preConsolidate` 拆詞／bleaching／short→long 閘門等大量複雜度；但「顯式段」
   **不能省**——unigram 記憶（無上下文、無法以 n-gram 表達，boosted unigram 會全語境過度支配）、
   顯式選字的釘住語意（`.withSpecified` 確定性 vs n-gram 統計性）、切分深度不匹配（split 記憶 vs
   2-key 節點，需 retokenization）、候選窗置頂 UX（n-gram grams 被選字窗排除）、寫入側觀察
   （`memorizePerception` 是 n-gram 語料生產者）。正確紅利＝「自動那半沉進引擎、顯式那半脫掉歷史包袱」。
   詳見報告 §八。
6. **方向五補充（2026-08-30：非狂拼自動段亦維持 override 套用的理由）**——P158 後續盤點
   確認「非狂拼（BPMF 一般拼音／磁帶／混雜）的自動 apply」在 S4 之後**仍維持原樣**，此為
   有意設計、非遺漏，理由：
   - **開關預設 off**：POM n-gram 統計（`pomAsNGramSourceEnabled`）是外源選項（預設關閉）；
     移交收益僅在使用者開啟開關時兌現——未開啟者行為完全不變。S4 已把狂拼自動段收斂，
     非狂拼維持原樣等同「把選擇權留給開關」。
   - **行為回歸風險**：override 是「強制覆寫」（記憶詞必出），n-gram 是「統計加分」（僅在
     DP 勝出時浮現）——一般拼音用戶依賴「打字中記憶詞直接浮現」的既有體驗，移交會使其
     變成「統計性浮現」，是行為退化而非等價替換。
   - **磁帶／混雜語義未驗證**：磁帶（quick-candidate／逐字語義）的組句查詢是否吃 POM n-gram
     注入、混雜（中英混打）的 POM 語義，皆未實作驗證——貿然移交可能破壞該模式既有行為。
   - **範圍界定成本**：S4-b/c 的教訓是「顯式選字路徑必須維持」（retokenization 重試、
     preConsolidate、bleaching、short→long 皆為顯式選字必要機制）；非狂拼移交需精確只動
     「自動 apply」、不動 `consolidateNode` 的 `.withSpecified` 與 POM 觀察，界線與逐路徑
     IH 測試成本不低。
   結論：維持「狂拼自動段已移交（S4-a）、非狂拼自動段與顯式段保留 override」的現狀；
   若日後要收斂非狂拼，先驗證「磁帶查詢是否吃 POM n-gram 注入」與「一般拼音對記憶詞強制
   浮現的依賴」再議（見 P158 報告附錄 D 的長遠評估／體系開放項）。

### 特殊備忘：為什麼 Beam Search 檢討現在不值錢

1. **Homa 的搜索空間已被硬上限框死**——`assignNodes` 的窗寬（`maxSegLength`）與笛卡爾乘積預算（10,000）是既有防禦體系，1D DP 在這種 DAG 上本來就便宜且**精確**（`Homa_PathFinder.swift` 每次組句都是線性掃描）。Beam Search 的本質是「拿近似換速度」，而這裡**沒有速度問題**——引入 beam 反而會引入近似誤差（可能選出次佳路徑），是純賠本買賣。
2. **專案裡真正需要「beam 思維」的地方已有歸宿**——`FuriousTypingSegmentor` 早就是「純閉包 DP/beam」在枚舉候選切分（P150 起，top-8）。若要擴大 N-best 處理，那是 **R3（δ 簡拼感知重切）** 或待決項「替代切分 Top-N 入窗」的內部工作，不是一個獨立的「Beam Search 可貫徹性」研究主題。
3. 唯一未來可能讓 beam 有存在感的情境，是「**Homa 要輸出 N-best 路徑**」（例如替代切分入窗、或 n-gram 體系需要多路徑評分）——但那時更對症的也是 **k-best DP**（每位置保留 top-k parent，精確、k 小）而非 beam。真要檢討，等那個需求出現再檢討也不遲。
