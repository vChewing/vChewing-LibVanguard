## Phase 142 實作結果（2026-08-16，兩倉：vChewing-macOS & vChewing-OSX-legacy；另有 vChewing-HomePage.io 的 credits 同步）

### 調查結論

- LineReader 使用點確認僅兩處（兩倉各自）：`LMConsolidator.checkPragma`（僅讀首行比對 pragma 標頭）、`LMCassette.open`（逐行解析 CIN2 磁帶）。
- LineReader 現行語義：僅以 LF 斷行、每行再 `trimmingCharacters(.newlines)`、EOF 回傳未終結的末行、不產生尾端空行。缺陷：`buffer.range(of:) + removeSubrange` 逐行搬移緩衝（接近 O(n²)），且 `String(data:)!` 強制解包——遇到非法 UTF-8 會直接崩潰。
- 殘留點盤點：macOS 倉 `Packages/RMJay_LineReader` 本地 SPM 套件、pbxproj wrapper 引用 2 處；Legacy 倉 `Shared/3rdParty/RMJay_LineReader.swift`、pbxproj 引用 4 處；兩倉 `AUTHORS` 與 `LICENSE.txt`／`LICENSE-CHS.txt`／`LICENSE-CHT.txt`／`LICENSE-JPN.txt` 各一行署名；HomePage `AUTHORS.md` 一行。
- 設計定案（應事主異議修正）：`ByteLineIterator` 直接持有 FileHandle 串流讀取（chunk 4KB），而非整檔載入——`checkPragma` 只讀首行時不必吃整份檔案、迭代器記憶體佔用以 chunk 為界。產出的 `ArraySlice<UInt8>` 與內部緩衝共享儲存，後續 `append` 觸發 COW 拷貝、已交出的切片不受影響；以 `consumed` 索引取代 `removeSubrange`，緩衝全消費時才 `removeAll(keepingCapacity:)`，消掉逐行搬移。
- 檢討後不施工項：LMCassette 解析迴圈全 byte-level 化——各 cell 最終均須具體化為 String 字典鍵，邊際收益而迴歸風險高。本次實得收益：消除 LineReader 的緩衝搬移與逐行 `.newlines` 字元集 trim、以及 force-unwrap 崩潰面。

### 變更（兩倉同型）

### 語義差異記錄

- 斷行依據由僅 LF 擴大至整個 `CharacterSet.newlines`（U+000A–U+000D、U+0085、U+2028、U+2029），CRLF 視為單一斷行（事主指定的刻意強化）。對 LF／CRLF 檔案與舊實作逐行一致（舊實作以 LF 斷行再靠 trim 削行尾 CR）；對內含 VT／FF／CR-only／NEL／LS／PS 的內容，舊實作會併成單行（僅削行首尾換行字元）、新實作逐行切開。byte-level 與逐 Character 等價的依據：這些純量皆屬控制類字元，grapheme break 規則保證其前後必斷（CR×LF 除外、恰為我們併為單一斷行的情形）；ASCII 位元組絕不會是 UTF-8 continuation byte，邊界掃描不會誤判。
- 非法 UTF-8 行：舊實作 force unwrap 會崩潰；新實作 `String(decoding:)` 以 U+FFFD 替換，屬防呆改善。
- CR-only（古典 Mac）檔案：新舊實作皆僅認 LF、整份視為單行；行尾孤立 CR 兩者皆剝除，行為一致。

## 要解決的問題

至少在 Session 處於 ascii mode 的時候，某些遠端桌面可能吃不到 flagsChanged 事件、從而導致一些在遠端電腦特殊場合下無法輸入某些「需要修飾鍵才能輸入」的字元。相關字元輸入全都變成了「沒有修飾鍵按下」的形態。

## Phase 147 實作結果（2026-08-26，兩倉：vChewing-macOS & vChewing-OSX-legacy）

> 本 Phase 由事主於「GitHub Issue `#605`: Rocky Linux 遠端登入密碼框右側 Shift 失效」調查期間發現的問題而提出，施術與提交由事主完成；術後報告依 KnowledgeMemo 的 Response Pattern 補完。該 Phase 不應被視為該工單的直接解決方案，除非今後被實證有效。

### 調查結論

- 根因：`InputSession_HandleEvent.handleKeyDown` 對所有 `.flagsChanged` 事件一律 `return true`（吞掉），客體 app 收不到任何修飾鍵的按下／放開事件。一般 app 依賴每個 keyDown 事件自帶的 modifierFlags 故無感；但遠端桌面類 app（如 Devolutions Remote Desktop Manager 這類 .NET 應用）自行以 flagsChanged 事件追蹤修飾鍵狀態集合——當 Session 處於英數模式（按鍵純放行）時，按鍵雖帶修飾鍵放行、遠端卻無從得知修飾鍵狀態集合發生變化，於是需要 Shift 才能輸入的大寫／符號全變成「無修飾」形態（`Z*#` → `z83`）。吞 flagsChanged 的行為與 Session 模式無關（各狀態皆發生），僅在英數模式放行按鍵時最容易被觀察到。
- 歷史回查：`if event.isFlagChanged { return ... }` 這個 early-return 為 `dbc9da95`（「IMKCandidates // Reorganization.」）為避免後續讀取 `event.characters?` 觸發 `NSInternalInconsistencyException` 而加（新增時即回傳 `false`）；2023-01-24 commit `984d4c71`（「SessionCtl // Change the way of handling `.flagsChanged`. - Learn something from mozc.」）把回傳值改成 `true`。經查 mozc 實作並不處理 keyup events——當年「向 mozc 取經」實為誤讀，該行為既不適用於唯音、也無助於修飾鍵狀態同步。本次保留 early-return（防崩潰仍必需），僅將回傳值改回 `false`（放行）。
- 順帶釐清（已寫入程式碼註解）：部分輸入法以「回傳 true 吞掉 flagsChanged」來阻止系統的雙擊空格全形句號替換，此舉屬邪修；正確作法為確認輸入法 Info.plist 未帶 `TISDoubleSpaceSubstitution` 欄位（不少副廠中文輸入法直接繼承系統注音輸入法的 TIS 屬性而把該欄位一併帶走；該欄位並非必需，唯音兩倉 plist 本無此欄位）。
- `handleCapsLockAndAlphanumericalMode` 的 `input.text.lowercased()`（Caps Lock 亮燈時的英數 commit）經覆核為刻意設計——使用者關掉系統 CpLk 中英輸入法切換後、CpLk 亮燈且未摁 Shift 時預設敲小寫英數。本次補註解鎖定該意圖，防止未來誤改。
