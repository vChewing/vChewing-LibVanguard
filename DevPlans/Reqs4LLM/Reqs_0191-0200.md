## 調查／根因（2026-09-07 完成調查並施術）

> 版本對照：本倉（`vChewing-macOS`／`vChewing-OSX-Legacy`）現行版本線為 4.7.x，4.7.3 SP1 Build 4731 即目前 head。上述 v4.9.2→v4.9.3 疑為事主所屬分發渠道／產品線之版本號；對照任務指示（「4.7.2 tag 之後引入、隨 4.7.3 曝露、提報者使用 4.7.3 sp1」），本卷以下以 4.7.2 tag→4.7.3 為分析座標。

- **機制**（兩倉同源同碼）：
  1. `@AppProperty`（SwiftExtension `SwiftFoundationImpl`）的 init 會在 key 缺席時把**預設值寫入 UserDefaults**。`kUserDataFolderSpecified` 的預設值＝空字串 `""`——於是「使用者從未手動指定過目錄」與「指定了空路徑」在 prefs 層無法區分（AppProperty seed 行為 3.8.4 起即存在、`""` 預設值 4.3.1 起即存在）。
  2. `LMMgr.dataFolderPath(isDefaultFolder: false)` 以 **key 是否存在**判定「是否使用者自訂」：空字串經 `expandingTildeInPath` 後仍為 `""`、再經 `ensureTrailingSlash()` 變成 `"/"` → 與預設目錄不等 → 進入合規性驗證 → `checkIfSpecifiedUserDataFolderValid("/")` 失敗（`/` 不可寫）→ `Broadcaster.confirmLmMgrDataFolderPathInvalidity("/")` → 彈出「…→ /…」警示（即客訴文案），隨後 `removeObject` 自癒。但 `PrefMgr.sharedSansDidSetOps` 等其他 PrefMgr 實體再初始化時會重新 seed `""` → 下一次 LM 存取再次誤判 → 重複彈窗——直到使用者手動設定一個「可寫目錄」（或原廠預設目錄）為止，與客訴完全吻合。

5. **「一個 dylib」的成立條件**：SwiftPM 一個動態 product ＝ 一個 dylib，且只能涵蓋**同一個 package** 的 target；**同 package 內多 target ＋ 單一 `.dynamic` product → 確實只產出一個 dylib**（實測：模組身分保留、可分別 `import`、exe 內零靜態副本）。反之「只挑子集動態化」必遭 SwiftPM 以 `error: … This will result in duplication of library code.` 拒絕——因 `Typewriter` 的依賴閉包（8 個 package）**完全落在** `MainAssembly4Darwin` 的閉包（25 個）之內。
6. **LGPL 集合盤點**：macOS 倉僅 `vChewing_Tekkon`／`vChewing_Homa` 標 `LGPL-3.0-or-later`，其餘跨平台模組為 MIT-NTL；而上游 `vChewing-LibVanguard` 的同一批模組**全數**標 LGPL——兩倉標頭不一致，**需事主定調**。`Tekkon`／`Homa` 的 package 依賴皆為空，故做成 `.dynamic` 後都是自足 dylib，且靜態 product 可依賴動態 product（實測：「靜態中介庫 → 動態庫」可建置，LGPL 符號完全不留在 exe 內）。

### SQLTrie 之死刑理由（本 phase 已執行）

1. **結構上不可能勝出。** 其查詢鏈為：`LIKE 'xxx%'` 掃 `keyinitials_id_map` → 讀出 JSON blob → 自家 byte-level 解析成 `Set<Int>` → 逐 node 再一趟 SQL 往返（靠 cached prepared statement 才堪用）→ base64 → 再以 `PropertyListDecoder` 解 entries blob。TextMapTrie 為「常駐 bytes 上的排序索引 ＋ 二分搜尋 ＋ UTF-8 byte 快路徑」——單一 pipeline、零往返、零中間 JSON、零 base64、零二次 plist 解碼。
2. **其自身設計即為自白。** 需要一個 7 秒 QueryBuffer 才「可用」；`useDFD` 預設 `false`（DFD 在非 Apple Silicon 反而更慢）。Phase 05 的記錄亦明言 partial-match 熱路徑的殘餘瓶頸「主要來自 SQLite fetch pattern 本身」。
3. **其自身測試即因效能而退役。** 本 phase 刪除的 `LXKitTests_Deprecated.swift` 開頭即寫「效能問題堪憂…該效能問題出在 SQLTrie 的 Constructor 上」。
4. **零生產消費者。** 下游自 Phase 06 / Phase 07 起全面改走 `vanguardTextMap`；在本 phase 手術前的樹中，SQLTrie 已無任何生產呼叫者。
5. **維持成本與收益不成比例。** vendored 8.5 MB `sqlite3.c`、一整套平台條件編譯旗標、兩份 manifest、兩個 BuildTool Plugin、一組平行 data builder。
6. **判斷的實質核心：此 workload 不需要資料庫。** SQLite 是交易型儲存引擎，而此處為唯讀、全量、單檔、以 prefix 查詢為主的辭典——其事務／寫入／併發保證一概用不到，卻須支付 B-tree 頁快取與語句機器的固定成本。故無論 SQLite 本身多快，它都不該勝過同一 process 內的 bytes 二分搜尋。**刪除的理由不是「SQLite 慢」，而是「這裡不該有資料庫」。**

### Plist 之死刑理由（本 phase 已執行）

核心結論：**「解碼慢但查詢快」的 tradeoff 並不存在。** 上表顯示 plist 在兩個軸上同時落後——啟動慢約 28 倍、查詢慢 12.11 倍、記憶體多約 7 倍；且 binary plist 連「可人工檢視／可 diff」這項除錯價值都不具備（TextMap 為 UTF-8 純文字，可直接 diff）。判死理由如下：

1. **從未進入任何自動化流程。** VanguardLexicon 的 `Plugins/` 現存僅 `TextTemplateAssetInjectorPlugin` 與 `VanguardTextMapPlugin`，**沒有 plist 專用 BuildTool Plugin**；`create_tiny_sample_plist.sh` 全倉無呼叫者。plist 一向只是 CLI 手動目標，從未被任何 pipeline 產出。
2. **下游零生產消費。** `vChewing-macOS` 與 `vChewing-OSX-Legacy` 對 `updateTrieFromPlistFile` 與 `.plist` 原廠辭典檔皆無命中；兩倉 vendored 的 TrieKit 副本中唯一的 plist 呼叫者，是 `vChewing_LangModelAssembly/Tests/TrieKitTests/TrieKit_Tests.swift:245` 的 round-trip 測試——與 LibVanguard 側 `TrieKit_Tests.prepareTrieLM()` 屬同一條測試。
3. **LibVanguard 內部同理。** `TrieHub.updateTrieFromPlistFile` 無生產呼叫者；其餘消費者僅 `TrieKit_Tests.swift:242-243` 與 `LXKitTests_TrieHub.swift:36`，即測試自測自。
4. **`Codable` 的服務對象單一。** `Trie` / `TNode` / `Entry` 的 `Codable` conformance 在 TrieKit 內別無消費者，僅為 `TrieIO.serialize` / `deserialize` / `save` / `load` 這條 plist 路徑而存在。

- `parseValueLine` 改回傳 `[Trie.Entry]` 後**少一趟映射**：原先是「tuple 陣列 → 再逐筆 `append` 成 `Entry` 陣列」，現在直接回傳 `[Entry]`，每條 VALUES 行省一次陣列走訪與一個中間陣列配置。
- `makeGramIdentityHash` 仍只雜湊 `keyArray`／`value`／`previous` 三欄（未動），故去重語義與雜湊成本不變。此處特意查過——若順手改用 `TrieGram` 的合成 `Hashable`，就會變成雜湊 5 欄，連帶改變去重行為。
- `TrieGram` 的合成 `Hashable` 目前**無人使用**（全庫無 `Set<TrieGram>` 或 `[TrieGram: …]`），故未引入任何新雜湊成本。
- `queryAssociatedPhrasesAsGrams` 的排序仍作用於內部那個 6 元 tuple（未動），排序路徑成本不變。

事主指示：只修 LibVanguard 的 Homa 折行，不追 legacy 的 `flatMap` 寫法差異。

三方比對結果（含 false alarm 更正）：Homa 共 16 檔，**10 檔三倉逐位元組相同**、**2 檔 MAC=LV 而 legacy 異**、**4 檔 MAC=LEG 而 LibVanguard 異**。其中「僅 LibVanguard 異」的 4 檔經判準（去空白後相同）確認為**純折行**：`Homa_Node.swift`（3 行）、`Homa_CandidateAPIs_FetchAndApply.swift`（10 行）、`Homa_CandidateAPIs_Revolver.swift`（7 行）、`Homa_PathFinder.swift`（5 行）。以 macOS／legacy 版覆蓋 LibVanguard 版後，四檔隨即三倉 sha256 全同。

**未動的兩處 legacy 差異**（皆非本次範圍）：

- `Homa_Assembler.swift` 的 **1 行差異（原先被我誤記為「純風格」，已更正）**：legacy 作 `flatMap { $0 }`、macOS 與 LibVanguard 作 `flatMap(\.self)`。**語義相同，但這不是可自由選擇的風格差異——是工具鏈能力差異。** 實測（兩側皆 `-swift-version 5`、各用自身 SDK 與 toolchain）：
  - Xcode 15（Swift **5.10**）：`[1,2,3].map(\.self)` ❌、`nested.flatMap(\.self)` ❌（`WritableKeyPath<_, _>` 未被綁定、`cannot infer key path type from context`）；但 `["aa"].map(\.count)` ✅、`let f: ([Int]) -> [Int] = \.self` ✅。
  - Xcode-Stable 與 Xcode（皆 Swift **6.4**）：上述四者全 ✅。
  - 兩側皆為 `-swift-version 5`，故與 `SWIFT_VERSION = 5.0` 之語言模式**無關**；差的是編譯器實作。
  - 根因是 **SE-0249 的 `\.self` 在「閉包回傳型別為泛型」的位置無法推斷 Root**，即 Swift 既有缺陷 [SR-12897](https://github.com/swiftlang/swift/issues/55343)（2020 年報、TypeChecker 標籤、Assignee: None）。**故 5.10 是踩到 bug，而非語言不支援。**
  - **精確起始版本無法在現機確定**：手邊僅有 5.10 與 6.4 兩級，缺 Xcode 16.x（Swift 6.0–6.3）之中間工具鏈，issue 頁面亦未載修復版本；可確定者為**介於 5.10 與 6.4 之間**。
  - **推論後果**：legacy **不可能**改用 `flatMap(\.self)`（編譯器拒絕）；要讓該行一致只有反向——把 macOS／LibVanguard 降回 `{ $0 }`，或升級 legacy 的工具鏈。這才是先前「Homa 三倉全等」在該行上的真實障礙。
  - 附帶：linter／formatter **不會**代為導正——三倉 `.swiftformat` 皆未啟用 `preferKeyPath`、三倉 `.swiftlint.yml` 亦皆未啟用 `prefer_key_path`（實測 legacy 對該檔零 `prefer_key_path` 報告）。
- `Homa_SwiftImpl.swift`：macOS 與 LibVanguard 多一份 `func has(string:) -> Bool`（約 25 行、純 Swift 無 Foundation 相依的子字串滑窗掃描）。根因是**模組邊界**：legacy 為單一 Xcode target，Homa 與 Tekkon 同模組，直接借用 `Tekkon/Tekkon_Utilities.swift:185` 的那份；macOS 的 `vChewing_Homa` 與 LibVanguard 的 `Homa` target 皆為 `dependencies: []`，看不到 Tekkon，故須自帶。此非可「修」之差異。

**附帶澄清（事主質問）**：Homa 三倉之間**不存在 Swift 6 專屬語法的差異**——`throws(`（typed throws）、`#if compiler(>=6`、`@retroactive`、`nonisolated(unsafe)`、`internal import`、`sending`、`~Copyable` 在三倉皆為 **0**；`Homa.Exception` 三倉逐位元組相同（普通 `public enum Exception: Error` ＋ `func … throws`）。另更正一項自身 false alarm：先前「legacy 有 4 處 `package`」實為 `CUSTOM_LGPLv3_EXCEPTION.md` 授權條文內的字樣，非 Swift 碼。

**驗證**：4 檔三倉 sha256 全同（`fc846d7dd4f18dca`／`04c63c048fb0a329`／`792a99429433de74`／`cfe08035c54ff2b0`）；LibVanguard（6.0／120）與 macOS（5.5／120）的 formatter 對該 4 檔皆 `0/4 files require formatting`；合併後各檔最長行 103～105 字元（≤120）；唯一 `line_length` 違規（`Homa_CandidateAPIs_Revolver.swift` 第 192 行、161 字元）在 **HEAD 版即已存在**（原為第 194 行），非本次引入，且因內容已三倉一致而為三倉共有；`vChewing-LibVanguard` `swift build` ✅ ＋ `swift test -c release --no-parallel` 各靶全綠（18/37/0/1/20/61/0/3）✅。macOS 與 legacy 未動。
