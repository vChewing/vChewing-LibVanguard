### 調查結論：三個模組皆可套用 Phase 127/128 手法，但各自有 caveat

實測 Swift memory layout：`String.Index` = 8B、`Range<String.Index>` = 16B、`(Range<String.Index>, Int)` = 24B、`String` header = 16B。

| 模組 | 現況結構 | 主要浪費點 | 預估節省 | 風險 |
|---|---|---|---|---|
| `LMCoreEX` | `[String: [Range<String.Index>]]` + `strData` + `temporaryMap` + `sortedKeysBox` | key String ×3 重複、dict bucket、per-key 小陣列、sortedKeysBox | 10k 筆時 ~1MB（~60%） | 中低 |
| `LMReplacements` | `[String: Range<String.Index>]` + `strData` | key String + dict 開銷 | 索引 −80% 以上（絕對值小） | 極低 |
| `LMAssociates` | `[String: [(Range<String.Index>, Int)]]` + `strData` | 24B tuple × 8.5 萬 | ~3MB（索引 −85%） | 中低 |

三者皆以「raw blob + sorted UInt32 index + binary search」取代 Dictionary。**儲存體決策（Kimi 修訂）**：`strData` 的實體改以 `[UInt8]`（UTF-8 bytes）常駐、descriptor 全部用 byte offsets（每行 16B）；但 **`strData` 對外必須維持 `String` 型別的 computed 唯讀屬性**（`String(decoding:as: UTF8.self)`），不可直接改型別——`LMInstantiator.retrieveData`（兩倉庫）、`MainAssemblyTests_Test2` 斷言、詞庫編輯器（`LMMgr_PhraseEditorDelegate` / `VwrSettingsPaneCocoaPhrases`）都直接讀 `.strData`，改型別會破壞呼叫端。`saveData()` 以 `String(decoding:as: UTF8.self)` 寫回，與處理後的輸入 bytes 完全一致（UTF-8 round-trip 無損）。查詢熱路徑的 cell 解析改為 byte 級掃描——與現行 `parseRanges`（`RangeParserAPI.swift`）的 ASCII 分隔符逐字節語義等價：**跳過空 cell、連續分隔符不產生空 cell、cell 索引 dense、尾端無分隔符的最後 cell 照常給出、閉包回 false 提早停止**（於 `RangeParserAPI.swift` 新增 `[UInt8]` 版共用 helper）；String 物化僅發生在最終 Gram 建構與 `dictRepresented` 等輸出點。全部為純 Swift 結構，macOS 10.9 / Linux / Windows 皆無相容性問題，不碰 NS 開頭類型。

### LMCoreEX（使用者片語 / 過濾清單 / 使用者符號）

**現況**：`rangeMap: [String: [Range<String.Index>]]`。每筆 key 的內容存在三份：`strData` 行內一份、Dictionary key 的 heap String 一份（`convertToPhonabets()` 轉換後的副本）、`sortedKeysBox` 再一份（partial match 查詢啟用時全量 keys 的 `[String]`）。

**10,000 筆估算**（奇摩/自然輸入法遷移使用者典型量級）：

| 項目 | 現況 | 改法之後 |
|---|---|---|
| key 索引 | 10k × (String ~40B + bucket ~21B) ≈ 0.61MB | keyData blob ~0.15MB + sorted entries 0.16MB |
| value 陣列 | 10k × (header 16B + 1.5×16B + 超配額) ≈ 0.46MB | 0（併入 entries） |
| `sortedKeysBox` | ~0.3MB（partial match 啟用時） | 0（prefix scan 取代） |
| `strData` 原文 | ~0.4MB | ~0.4MB（不變） |
| **合計** | **~1.7MB** | **~0.7MB** |

**改法**：每行一個 descriptor `(keyStart, keyEnd, lineStart, lineEnd)` = 16B（一行只屬於一個 key、value 即整行 → 不需 valueOffsets flat 陣列，與 TextMapTrie 的 KeyEntry 同型），加上轉換後 keys 的專屬 `keyData: [UInt8]` blob。節省隨筆數線性成長（20k 筆 → ~2MB）。

**⚠️ caveat**：key 是 `convertToPhonabets()` 轉換後的注音字串，不是 `strData` 原始子字串 → 必須有專屬 `keyData` blob。`temporaryMap`、`saveData()`、reverse 模式、省略單漢字邏輯、`dictRepresented` 全不受影響。行為契約由 `LMCoreEXTests` 現有 6 項測試定義。

**⚠️（Kimi 補充）實作時需逐條複刻的語義細節**：(a) `replaceData` 開頭 tab→space 取代**先於**「與現有內容相同則提前返回」的比對，且 `strData` 保存的是正規化後內容；(b) `replaceData` 會連 `temporaryMap` 一併清空；(c) `saveData()` 先寫原文、再把 `temporaryMap` 逐筆以 `"值 鍵 權重\n"` 格式**合併寫回**（原案未提，漏掉會丟暫存詞）；(d) 同 key 的行須依檔案行序排列（`gao1 == ["篙","糕","膏","高"]` 斷言依賴）→ 排序需以 lineStart 為 tie-breaker；(e) 第三欄權重的 `#` 檢查是「cell 內含 0x23 即視為壞權重」；(f) `keys(matchingPrefix:)` 的下界搜尋以一般字典序比較即可（entry key 以 prefix 開頭且更長時視為不小於 prefix）。

### LMReplacements（語彙置換表）

**三個模組裡最乾淨的一例**：key 是 `strData` 的原始子字串、無任何轉換 → 連 `keyData` blob 都不需要，entry 直接指 `strData`：`(keyStart, keyEnd, lineStart, lineEnd)` = 16B/key，取代現在「heap String + dict bucket + 16B range」約 100B/key 的開銷。

**⚠️（Kimi 補充）重複 key 語義**：現行 `newMap[theKey] = theRange` 是「同 key 時最後一行覆蓋先前內容」；sorted entries 去重時必須保留 lineStart 最大者，不可保留先出現的行。

**熱路徑注意**：`isPhraseReplacementEnabled` 時 `unigramsFor` 會逐 unigram 查一次 `valuesFor(key:)`。Dictionary O(1) 換成 binary search O(log n)，對幾百筆的小表是 ~9 次短字串 byte 比較，可忽略（Phase 129 的 wildcard 匹配比這複雜得多都無感）。風險極低；缺點只是絕對節省量小（使用者置換表通常僅數 KB）。

### LMAssociates（關聯詞語）

**實測原廠 template**（`vChewing-VanguardLexicon`）：cht 3,987 行 / **42,558** 個 value cell；chs 3,870 行 / **42,350** 個 value cell；合計 ~85k values、~7.9k keys、~446KB 原文。

**現況常駐估算**：85k × 24B tuples ≈ 2.04MB + keys/dict ~0.6-0.8MB + per-key 陣列 ~0.3MB + `strData` ~0.45MB ≈ **3.3-3.7MB**。

**改法**：每行的所有 value 是同一行內**連續 cells**（最長一行 79 個 value）→ 每 key 存 per-line descriptor `(lineStart, lineEnd, cellStart, cellCount)` = 16B/行。7.9k 行 × 16B ≈ 126KB + key blob ~40KB + entries ~126KB + `strData` 0.45MB ≈ **0.75MB 總計**（索引 −85%，淨省 ~3MB）。

**⚠️ caveat**：key 經 `cnvNGramKeyFromPinyinToPhona()` 轉換 → 需要 key blob。查詢語義（`pair.toNGramKey` 與 `pair.value` 雙鍵查詢 + dedup、`dictRepresented` 匯出）皆可保留。lazy load 已存在（Phase 127 時做的）。目前無專屬測試檔案，行為由 `LMInstantiator` 相關測試涵蓋。

**⚠️（Kimi 補充）實作時需逐條複刻的語義細節**：(a) cell 0 首 byte 為 `#` → 整行跳過；value cell 遇首 byte `#` → **該行後續 cells 全部不錄**（`valueCellCount` = 停止前已錄數）；(b) key 無 value cell 的行不建 entry；(c) `cnvNGramKeyFromPinyinToPhona` 內的 `convertToPhonabets` 對**純英數 pinyin 不生效**（`isNotPureAlphanumerical` 檢查），實務上 key 多原樣保留——屬既有行為，測試不得假設 pinyin 會被轉成注音；(d) `dictRepresented` **不做 dedup**（與 `valuesFor` 不同），同 key 多行依行序全數列出。

### 行為保留契約（不得破壞）

- 同 key 內 value 順序 = 檔案行序（`LMCoreEXTests` 斷言依賴，如 `gao1 == ["篙","糕","膏","高"]`）。
- `temporaryMap` 保持 `[String: [Homa.Gram]]` 且為唯一可變點；`insertTemporaryData` / `clearTemporaryData`（`LMInstantiator.swift`）直接寫入與清空；`clear()` 連同 temporaryMap 一併清空。
- `keys(matchingPrefix:)` 維持「sorted 主表 + sorted temporaryMap 合併、去重」語義（`testPartialMatchIncludesTemporaryMap` / `testPrefixMatchingDeduplicatesOverlappingMainAndTemporaryKeys` 依賴）。
- 解析規則不變：`#` 開頭行跳過、`replaceData` 開頭 tab→space 取代、第三欄含 `#` 視為壞權重（`defaultScore` 兜底）、`forceDefaultScore` 強制。
- `dictRepresented`（`summarize(all:)` 五模組全用）、`dump()`、`count`（唯一 key 數）、`isLoaded`、`saveData()`（原文寫回、不得正規化）全部保留。
- （Kimi 追加）`strData` 對外維持 `String` 型別 computed 唯讀屬性，值與處理後原文一致（`retrieveData` / 詞庫編輯器 / MainAssembly 測試依賴）。
- （Kimi 追加）LMReplacements 同 key 重複時「最後一行生效」。
- 省略單漢字過濾（`omitNonTemporarySingleCharNonSymbolUnigrams` + `factorySingleReadingValueHashes`）沿用現行物化時 `hashValue` 邏輯。
- LMAssociates `valuesFor(pair:)` 雙鍵查詢 + `deduplicated`、`hasValuesFor` 語義不變。
- 純 Swift 實作，macOS 10.9 / Linux / Windows 相容、不碰 NS 開頭類型。

### 後續評估：`refreshExisting` 細粒度化提案（經評估不施工）

曾評估將 `.refreshExisting` 改為帶 nullable keyArray 參數的 parameterized enum case：參數有效時僅對「讀音鏈與參數完全吻合的節點」重新查詢並更新 grams，空陣列依 nil 處置（全量刷新）。評估結論為**不施工**，理由：

- **正確性漏洞（partial match）**：開啟 partial match 時，讀音鏈為前綴 `q` 的節點也能查到 chain 為 `X` 的使用者片語（gram 的 actual keyArray 長於 span）。exact-chain 過濾會漏掉這些前綴節點；刪詞情境下已刪的詞會繼續出現在其候選中。複合讀音鍵 spans 的 alternative 鏈亦無法以純 `[String]` 完全吻合表達。
- **呼叫端負擔**：詞庫編輯器為批次儲存，呼叫端無法可靠枚舉受牽涉的 chains，漏傳即產生靜默陳舊節點；現行全量刷新是防彈設計。
- **投入產出不成立**：`refreshExisting` 屬人肉操作頻率的罕見路徑，不在敲鍵熱路徑；快取清空後數次敲鍵內自然回暖。安全的替代粒度（僅作廢「chain 為 X 之前綴閉包」的快取項目、仍重掃全部 segments）雖無正確性問題，但收益依舊邊際，卻需新增 API 表面與測試並承擔呼叫端誤用風險。

1. `@backDeployed` **要求 `public`** —— `private` / `fileprivate` / `internal` 全部被編譯器拒絕。
2. `@backDeployed` **要求 `final`** —— `FileHandle` 是 non-final class，須加 `final` 修飾詞繞過。

### 核心決策：Node 改 Struct，捨棄對象池

**heap 分配來源分解**（每次敲鍵 `resizeGrid + assignNodes + assemble`）：Node class 實例（每新節點 1 次）+ 每節點三個 heap 容器（`grams: [Gram]` 陣列、`bigramMap: [String: [Gram]]` 派生字典、`allActualKeyArraysCached: Set` 派生集合）。典型 10 鍵組字區 ~55 節點，即每次敲鍵數百次 malloc/free。

**對象池（associated type / 專用構建析構）被否決**：
- 池化救不了大頭——`bigramMap` / `Set` 內容每次全變，池化 class 實例無法消除 container 重建；
- Node 被 `fetchOverlappingNodes` 等 API 到處外遞，歸還時機追蹤易錯。

**struct 化一舉三得**：Node 本體不佔 heap（值嵌於 segments 字典槽位）、segments / 字典在 COW 唯一引用時原地更新不重新分配、容器 buffer 隨值複用。

### 修法

- **`Homa.Node` 由 `public final class` 改為 `public struct`**（Codable / Equatable / Hashable 表面保留；`copy` / `init(node:)` 保留「識別碼全新」語義）。`syncingGrams` / `selectOverrideGram` / `reset` / `getScore` 全部改 `mutating`。

## Phase 137 實作結果（2026-08-08 完工，macOS Repo & Legacy Repo）

### 設計總覽

唯音輸入法的 `NotifierUI` 原本是「multiple NSWindow / NSPanel」設計：每次通知各建一個 borderless
`NSWindow`、常駐最多 4 個實例，舊視窗依堆疊位置淡出、1.3 秒後滑出並 `close()`。Apple Silicon 上
macOS 26 起 NSWindow 基礎開銷龐大——本手術改為**單一常駐透明 NSWindow + 卡片堆疊**，並把
「幾何與序列」的全部計算抽離為純計算的 singleton viewModel，前端只做呈現。

- **後台計算**：`NotifierViewModel`（NotifierUI target 內獨立檔案，純計算 singleton）——堆疊增刪 / 逐出 /
  去重 / 淡出狀態 / 滑入旗標、`layout(in:)` 輸出全部幾何、時間軸以明確方法呼叫驅動。
- **前端純渲染**：`Notifier` / `NotifierCard` 僅負責綁定視圖實例、套用計算結果、排程計時器與動畫。
- **單元測試**：以 Swift Testing Macro 鎖定後台計算數據（15 項），不再依賴實機目視。

### 後台計算（NotifierViewModel，NotifierUI target 內獨立檔案）

- **堆疊狀態**：`records`（邏輯記錄：id / message / intrinsicWidth / isNew / isFadingOut /
  needsSlideIn；索引 0 = 最新）。`enqueue` 滿 3 張時逐出最舊者；與最新且仍在新鮮期（0.3s）內者
  重複則略過；空訊息（含僅換行）拒絕。
- **基礎透明度**：`baseAlphas = [1.0, 0.6, 0.05]`（新 → 舊：100% / 60% / 5%）；淡出中為 0。
- **`layout(in:)` 輸出全部幾何**：視窗框架（高度固定（`windowHeight` = 三卡 + 兩間距 + 兩側 `windowPadding` 留白），寬度以
  最寬卡片為準）、每張卡片的 frame / alpha / 滑入起點。**每張卡片依自身內容寬度**（SwiftUI
  語義上的 fixedSize），並以**尾端（右緣）對齊**於同一螢幕位置（右緣 `maxX − 20`）。
- **時間軸**：`markNotNew` / `fadeOut` / `completeRemoval` / `consumeSlideIn` 皆為明確方法呼叫
  （測試可直接驅動、不需等待真實時間）；時序常數由前端據以排程——`dedupWindow` 0.3s、
  `displayLifetime` 1.3s、`slideInDuration` / `relayoutDuration` 0.1s、`fadeOutDuration` 0.15s。

### 前端（Notifier / NotifierCard）純渲染

- **視窗**：單一常駐 borderless `NSWindow`，`isOpaque = false` / `backgroundColor = .clear` /
  `hasShadow = false` / `ignoresMouseEvents = true`；高度固定（`windowHeight`）、本身不參與任何動畫
  （`setFrame(_:display: false)` 直接就位）——避免視窗動畫與 subview 動畫相互干擾。
- **卡片**：`NotifierCard` 自帶材質背景 layer（10.10+ `NSVisualEffectView`、`underWindowBackground`
  材質 10.14+、其餘（macOS < 10.10）以純色填充）與逐卡陰影；**macOS < 10.13** 的透明視窗
  不渲染 CALayer shadow——以 1px 灰邊（`layer.border`，隨 alpha 等比淡化）替代陰影；
  視窗內側留白（`windowPadding`，需設得夠大以免橫向滑入動畫時視窗邊緣切到陰影）供陰影繪製，

### 設計總覽

LMAssembly 套件（含 vendored TrieKit）的打字熱路徑清理，目標是消除每次查詢／每次敲鍵的一次性小分配：

- `getCachedSplit`：每次呼叫的字串插值 key 改為複合 Hashable key struct。
- `TrieStringPool`：LRU touch 的 O(n) `firstIndex(of:)` + `remove(at:)` 改為 FIFO 逐出。

### 修法

- **`TrieStringOperationCache.getCachedSplit`（`TrieKit_PerformanceUtils.swift`）**：`let key = "\(string)|\(separator)"`（每次呼叫 1 個插值 String）改為 `SplitCacheKey(string:separator:)` 複合鍵 struct（`Character` 為 Hashable；`(string, separator)` 對 key 為單射、快取語義完全一致）。
- **`TrieStringPool.internKey` / `internValue`**：刪除 `touchKey`／`touchValue` 及其呼叫（每次 cache hit 的 O(n) `firstIndex(of:)` + `remove(at:)` + `append` 掃描位移），逐出改為純 FIFO（插入序 append、`evictKeyIfNeeded`/`evictValueIfNeeded` `removeFirst()`）。語義依據類別 doc 既有註記：「被淘汰的字串只會失去未來 deduplication 的機會，不會影響已回傳的 String reference」——回傳值不變，僅逐出策略由 LRU 改 FIFO；doc 同步更新。`maxPoolSize`（10,000）、`clear()`、`@usableFromInline` 表面不變。
- **`LMInstantiator.unigramsFor` miss 管線**：`rawAllUnigrams` 追加 `reserveCapacity(max(16, flatKeyArray.count * 8))`（純緩衝預先擴容）；`dataAsFilter` 由 `.map(\.current)` 改 `.lazy.map(\.current)` 直送 `Set.init`（省 1 個中間 `[String]`）。
- **`Array<Homa.Gram>.consolidate(filter:)`（`HomaCompatShims.swift`）**：`filter { ... }.forEach { ... }`（1 個中間陣列）改為單趟 `for neta in self`——先 filter 後 dedup、first-occurrence wins、順序保留，語義逐字節一致。
- **`LXPerceptor.getSuggestion`**：把迴圈不變式 `effectiveKeyArray = keyArrayForCandidate.isEmpty ? [frontEdgeReading] : keyArrayForCandidate` 提升到迴圈外（空鍵陣列分支不再每輪重建）。

### 行為保留契約

- `getCachedSplit`／`internKey`／`internValue` 回傳值不變（dedup 不變，僅逐出策略 LRU→FIFO）。
