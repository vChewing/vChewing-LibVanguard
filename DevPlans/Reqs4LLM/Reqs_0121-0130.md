## Phase 121 實作結果（2026-07-28, macOS Repo & Legacy Repo）

### 逆向工程發現

對 `IMK-Mavericks`（x86_64）與 `IMK-GoldenGate`（arm64e）的 `InputMethodKit.framework` 進行了符號分析與反組譯：

#### 1. IMKServer 的 NSMenu 快取機制（✅ 無洩漏）

```asm
; -[IMKServer _setCachedMenu:] (Mavericks x86_64)
movq  _cachedMenu(%rip), %rcx    ; 載入舊快取 menu
movq  (%rax,%rcx), %rdi
callq *release                     ; [oldMenu release] ← 正確釋放
callq *retain                      ; [newMenu retain] ← 正確保留
; 存入 ivar
```

IMKServer 的 `_setCachedMenu:` 在 MRC 環境下先 `release` 舊 menu 再 `retain` 新 menu。同一個 ivar（`_OBJC_IVAR_$_IMKServerPrivate._cachedMenu`）在 GoldenGate 拆分為 `_IMKServerPrivateLegacy._cachedMenu` 與 `_IMKServerPrivateModern._cachedMenu`，兩者行為一致。**IMKServer 的快取機制沒有洩漏。**

#### 2. IMKServer._actionsFromMenu:（✅ 無洩漏）

`_actionsFromMenu:` 遍歷 `[menu numberOfItems]` → `[menu itemAtIndex:]`，對每個 item 讀取 `hasSubmenu` / `submenu` / `action` 等屬性，收集至 `NSMutableArray` 後回傳。過程中不額外 retain menu item。

#### 3. IMKInputSessionController.menu（⚠️ 跨語言橋接邊界）

```objc
- (nullable NSMenu *)menu {
    if (_IMKSwift_onProvidingIMEMenu)
        return _IMKSwift_onProvidingIMEMenu((uintptr_t)self);
    return [[NSMenu new] autorelease];
}
```

Swift block（ARC 管理）→ ObjC MRC 的跨語言橋接產生 autoreleased 暫存物件（NSMenuItem / NSAttributedString / 被 nulled 的選單項目等），全部堆積在主事件迴圈的 autorelease pool 中。menu callback 被呼叫的頻率雖不高，但每次呼叫產生的 transient 物件在 pool drain 前會被 Instruments 視為「仍在 heap 上的活物件」。

### 修復方案

在 `IMKSwift.m` 的 `-[IMKInputSessionController menu]` 中，為 block 呼叫包一層 `@autoreleasepool`，確保每次選單建構產生的 autorelease 暫存物件在函式返回前即刻釋放：

```objc
- (nullable NSMenu *)menu {
    if (_IMKSwift_onProvidingIMEMenu) {
        NSMenu *menu = nil;
        @autoreleasepool {
            menu = [_IMKSwift_onProvidingIMEMenu((uintptr_t)self) retain];
        }
        return [menu autorelease];
    }
    return [[NSMenu new] autorelease];
}
```

關鍵 MRC 語義：
- `retain` 在 pool drain 前保護回傳的 NSMenu 物件不致提前釋放
- `autorelease` 將 NSMenu 以 Cocoa 慣例（+0 autoreleased）交還給呼叫方（IMKServer）
- `@autoreleasepool` 確保 nulled menu item、內部 attributed string、i18n 暫存字串等在函式返回前全部釋放

## 要解決的問題

唯音輸入法原始設計上來講是允許「單獨輸入聲調」的。這個功能有相關的綁定開關（與聲調鍵行為有關）。
該功能有啟用的話，單獨輸入聲調時，會出現工具提示，大致提示這些內容：

- 「敲空格鍵以插入組字區」
- 「敲 Enter 以遞交」
- 「該聲調亦會嘗試與接下來輸入的注音相結合」

其中第一項與第三項沒問題，但第二項失效了。請嘗試解決。

## Phase 122 實作結果（2026-07-29, macOS Repo & Legacy Repo）

### 根因分析

獨立聲調輸入後敲 Enter 之所以不生效，關鍵在於 `BPMFFullMatchTypewriter` 的 `handleStandaloneIntonation` 方法對 Enter 鍵缺少處理路徑：

1. 使用者輸入聲調鍵（如「ˊ」）後，composer 僅含聲調（`hasIntonation(withNothingElse: true)`），此時會顯示工具提示。
2. 使用者敲 Enter 時，`consumeReadingInputIfNeeded` 將空白（`" "`）餵入 composer 作為確認鍵（`confirmCombination`），但空白在大千佈局映射回自身（`mapQwertyDachen[" "] = " "`），而空白是合法聲調（`allowedIntonations` 包含 `" "`），因此 composer 的聲調從「ˊ」被覆寫為「 」。
3. `getComposition()` 內部以 `.swapping(" ", with: "")` 移除空白，導致 `phonabetKeyForQuery(pronounceableOnly: false)` 回傳 nil，進入 `handleStandaloneIntonation` 的 nil-key 分支。
4. 原有程式碼僅處理了 `input.isSpace` 的情況（將聲調插入 assembler），對 Enter 鍵則直接 `clear()` 掉 composer 後返回 nil，導致後續 `triageByKeyCode` → `handleEnter` 嘗試提交時 composer 已被清空，無內容可供遞交。

### 修復方案

在 `handleStandaloneIntonation` 的 `phonabetKeyForQuery(...) == nil` 分支中，新增 Enter 鍵處理：

- 若 `existedIntonation.isValid`（composer 在被空白覆寫前確有合法聲調），則直接將該聲調符號作為 `State.ofCommitting` 遞交。
- `existedIntonation` 在 `handle()` 起始即被快取（早於 `consumeReadingInputIfNeeded` 對 composer 的修改），因此能正確保留原始聲調（如「ˊ」）。

### 程式碼變更

**`vChewing-macOS/Packages/vChewing_Typewriter/Sources/Typewriter/Typewriter/Typewriter_BPMFFullMatch.swift`**:
- `handleStandaloneIntonation` 方法：在 `input.isSpace` 分支之後、`handler.composer.clear()` 之前，新增 `input.isEnter && existedIntonation.isValid` 分支，直接遞交原始聲調符號。

**`vChewing-OSX-legacy/Shared/vChewingComponents/Typewriter/Typewriter/Typewriter_BPMFFullMatch.swift`**:
- 同上，鏡像同步。

### 測試新增

- 新增 `test_IH115_StandaloneIntonationEnterCommitsToneMark`：模擬敲聲調鍵「6」（大千佈局映射至「ˊ」），驗證 composer 處於 standalone intonation 狀態（`hasIntonation(withNothingElse: true)`、tooltip 非空），再敲 Enter 確認遞交了「ˊ」。

## 要解決的問題

目前唯音輸入法在與 IMK 的互動上已經到了記憶體管理藝術上的最優解。然而，唯音輸入法的記憶體管理仍有需要改良的地方、且這次的改良對象範圍鎖定到了 `Homa (Assembler) <--> Lexicon` 這個 heap 劇變區。

DeepSeek-v4-pro-max 經過調研之後，給出的一個可行思路或可落實：在 **Swift 內做 scratch buffer 複用**。Pseudo code 如下：

```swift
// 現狀：每次查詢 new array
func getNodeIDs(for key: String) -> [Int] {
    var ids: [Int] = []   // ← alloc
    // ... 查詢邏輯
    return ids
}

// 改良：傳入可複用的 buffer
func getNodeIDs(for key: String, into ids: inout [Int]) {
    ids.removeAll(keepingCapacity: true)  // ← 不 alloc
    // ... 查詢邏輯，append 到 ids
}
```

> 把 Homa 的 `gramQueryCache` 和 TextMap 的 `getNodeIDsForKeyArray` 沿線改成 `inout` buffer 傳遞，6.5 小時內可從 149K alloc 降為 ~10 個以內的 long-lived buffer。**效果等同 Rust，無需換語言。**

## Phase 124 實作結果（2026-07-30, macOS Repo & Legacy Repo & LibVanguard）

### 設計思路

6.5 小時打字的 heap dump 顯示 149,253 個 `[Int]`、95,936 個 `[UInt8]`、70,045 個 `StringStorage`——這些都是 Homa ↔ Lexicon 熱路徑上的暫態物件。問題不在洩漏（ARC 已釋放），而在 **alloc/dealloc churn** 導致的 heap fragmentation（malloc zone 不立即歸還 OS）。

本次手術採用雙策略：

1. **QueryBuffer 追加 count limit**：原先僅以 7 秒時間過期，無上限。密集打字時快取可膨脹至數千條目，每個條目都是一個 `[Int]` 陣列。新增 `maxCount` 後，達上限時逐出最舊條目，將 active array 數目收束至常數。

2. **TextMapTrie 內部 scratch buffer**：`getNodeIDsForKeyArray` 在 cache miss 時原先每次 `var matchedNodeIDs = [Int]()` 分配新陣列。改為 `scratchNodeIDs.removeAll(keepingCapacity: true)` 複用——只有最終的快取儲存才做一次 `Array(scratchNodeIDs)` copy。

| `init(expirationInterval:maxCount:)` | 新增 `maxCount: Int? = nil` 參數（nil = 舊行為，無上限） |
| `set(hashKey:value:)` | 尾端新增 `evictOldestIfOverMaxCountLocked(now:)` 呼叫 |
| `evictOldestIfOverMaxCountLocked` | 新方法：掃描快取找 timestampNs 最小條目並移除；每次 set() 最多逐出 1 條 |

## 要解決的問題（大致方向）

針對 VanguardTextMap 套件的資料索引部份探究如何節省記憶體。

## 可實際著手的地方（細緻方向）

以下皆針對 `TrieTextMap_Core.swift` 中 `TextMapTrie`（或 `vChewing-LibVanguard` 中的 `_TextMapTrie<Buffer>`）的常駐索引結構提出，**不涉及 mmap**。

| 方向 | 位置 | 預估節省 | 難度 | 說明 |
|------|------|----------|------|------|
| `valuesLineOffsets` Int→UInt32 | `TrieTextMap_Core.swift:131` | 3–5 MB | 低 | VALUES 每行起始 offset 改用 4 bytes 儲存；txtMap 僅 13.6 MB，offset 不可能超過 UInt32 範圍。 |
| `KeyEntry` 欄位縮小 | `TrieTextMap_Core.swift:84-92` | 5–7 MB | 低 | `keyStart/keyEnd/startLine/count` 改用 `UInt32`，`segmentCount` 維持 `UInt8`；可降低每個 entry 的對齊後大小。 |
| `reverseLookupTable` CSR 化 | `TrieTextMap_Core.swift:94-97`、`buildReverseLookupTable()` 在 `TrieTextMap_Core.swift:457-525` | 2–5 MB | 中 | 改以三個 flat array（`keys: [UInt32]`、`lineIndexOffsets: [UInt32]`、`lineIndexValues: [UInt32]`）取代每個漢字一個 `ContiguousArray` + `[Int]`，消除大量小 heap allocation。 |
| `keyInitialsIDMap` 去 Dictionary 化 | `TrieTextMap_Core.swift:134 | 1–3 MB | 中 | `[String: [Int]]` 中每個首字組合都是一個 `String` + 一個 `Array`。可改用 sorted array 或 byte-pool + offset 結構。 |
| Lazy reverse lookup | `buildReverseLookupTable()` 在 `TrieTextMap_Core.swift:457-525` | 延後尖峰 | 中 | `reverseLookupTable` 與 `valueLineToKeyEntryIndex` 都服務反查；若反查非啟動後立即使用，可延遲到第一次 `reverseLookup(for:)` 再建立。 |
| intern pool 容量上限 | `TrieStringPool.shared`、`TrieStringOperationCache.shared`（由 `resolveKey()` 在 `TrieTextMap_Core.swift:852-856` 與 `resolveKeyArray()` 使用）| 看情境 | 中–高 | 兩個全域單例 pool 目前只增不減；可考慮 LRU eviction，但需確認是否影響正確性或引發 dangling substring。 |

### 各方向詳細說明

#### 1. `valuesLineOffsets: [Int]` → `[UInt32]`

`TrieTextMap_Core.swift:131`：
```swift
private let valuesLineOffsets: [Int]
```
VALUES 行數對 factory dict 約 60–80 萬行。每個 offset 用 8 bytes 的 `Int` 過大；改 `UInt32` 可減半。

#### 2. `KeyEntry` 結構縮小

`TrieTextMap_Core.swift:84-92`：
```swift
private struct KeyEntry {
  let keyStart: Int
  let keyEnd: Int
  let startLine: Int
  let count: Int
  let segmentCount: UInt8
}
```
對齊後約 40 bytes/entry。因為 offset 與 line number 都 < 2³²，可改為：
```swift
private struct KeyEntry {
  let keyStart: UInt32
  let keyEnd: UInt32
  let startLine: UInt32
  let count: UInt32
  let segmentCount: UInt8
}
```
預估壓到 17 bytes（對齊後約 20–24 bytes）。

#### 3. `reverseLookupTable` CSR 化

`TrieTextMap_Core.swift:94-97`：
```swift
private struct RevLookupEntry {
  let key: ContiguousArray<UInt8>
  let lineIndices: [Int]
}
```
目前每個漢字都是兩個獨立 heap allocation。對 2–3 萬個不同漢字，object header 與對齊損失明顯。可改為：
```swift
private struct ReverseLookupIndex {
  let keys: [UInt32]            // 每個漢字的 Unicode scalar value
  let lineIndexOffsets: [UInt32] // lineIndexValues 的 range start
  let lineIndexValues: [UInt32]  // 所有 line indices 連續存放
}
```
`reverseLookupIndex(for:)` 改對 `keys` 做 binary search，再用 offset 讀出對應 line indices。

#### 4. `keyInitialsIDMap` 去 Dictionary 化

`TrieTextMap_Core.swift:134`：
```swift
private let keyInitialsIDMap: [String: [Int]]
```
首字組合數量有限，但 `Dictionary<String, [Int]>` 讓每個組合都帶 `String` 與 `Array` 的 heap object。可改用：
```swift
private struct InitialsBucket {
  let initialsUTF8: ContiguousArray<UInt8>
  let nodeIDs: [UInt32]
}
private let keyInitialsBuckets: [InitialsBucket]  // sorted by initialsUTF8
```
查詢時以 binary search 或 prefix trie 定位 bucket。

#### 5. Lazy reverse lookup

`buildReverseLookupTable()` 在 `TrieTextMap_Core.swift:457-525` 與 `buildLineOwnerIndex()` 在 `TrieTextMap_Core.swift:434-448`：

`valueLineToKeyEntryIndex`（`[Int32]`）與 `reverseLookupTable` 都只服務 reverse lookup。可在第一次需要反查時再建立，降低啟動瞬間的 RSS 尖峰。缺點是第一次反查會有延遲，且若之後頻繁使用，總量不變。

#### 6. intern pool 容量上限

`TrieStringPool.shared` 與 `TrieStringOperationCache.shared` 在 `resolveKey()`（`TrieTextMap_Core.swift:852-856`）與 `resolveKeyArray()`（`TrieTextMap_Core.swift:858-863`）中被呼叫。目前兩個 pool 只增不減。若查詢覆蓋的 reading key 範圍很廣，pool 會持續成長。可評估加入 LRU eviction，但需確保不會產生 dangling `Substring` 或影響已有 reference。

### 備註

上述優化主要壓縮輸入法本體索引的常駐記憶體，理論上可把 factory dict 相關索引從 20–30 MB 降至 10 MB 左右；但無法處理 Apple Silicon 上開啟/關閉 Settings 後由系統/framework/SwiftUI/Liquid Glass 產生的額外開銷。

### 補充調查：原廠反查資料實際使用範圍與 UTF-8 共享儲存可行性

#### 1. 原廠反查資料（`TextMapTrie.reverseLookup`）的使用範圍

經掃描 `vChewing-macOS` 倉庫，`factoryTrie?.reverseLookup(for:)` 與其包裝 `LMAssembly.LMInstantiator.getFactoryReverseLookupData(with:)` 的實際使用點如下：

| 使用點 | 檔案 | 說明 |
|--------|------|------|
| 獨立反查視窗 | `MainAssembly4Darwin/RevLookupUI/CtlRevLookupWindow.swift` | 輸入法選單「RevLookup」或熱鍵觸發，逐字查詢並顯示原廠讀音。 |
| 公開 API 包裝 | `LangModelAssembly/LMInstantiator_TextMapExtension.swift` | `getFactoryReverseLookupData(with:)` 是原廠反查對外的唯一包裝。 |
| 協定層後門 | `TrieKit/TrieTextMap_Core.swift` | `reverseLookupEntryGroup(for:)` 在 `VanguardTrieProtocol.getEntryGroups(filterType: revLookupEntryType)` 路徑提供反向條目群組；目前無 vChewing 執行期路徑呼叫此 `filterType`。 |

結論：原廠反查索引在啟動後若未被使用者手動開啟 RevLookup 視窗，實際上處於閒置狀態。這支撐了「方向 5：Lazy reverse lookup」的安全性——將 `valueLineToKeyEntryIndex` 與 `reverseLookupTable` 延遲到第一次 `reverseLookup(for:)` 才建立，不會影響日常打字或候選字窗顯示。

#### 2. `utf8View` / `Substring` 共享儲存的可行性

Swift 確實有類似 `utf8View` 的單位：

- `String.UTF8View`（`String.utf8`）與 `String.UnicodeScalarView`（`String.unicodeScalars`）是零拷貝 view，可對同一 `String` 儲存做不同層級的解讀。
- `Substring` 是 `String` 的切片，與來源 `String` 共享儲存區；只要來源 `String` 存活，`Substring` 就不會額外分配 heap 記憶體。

然而這些特性無法直接解決 Trie 內部的「從 raw `Data` 產生 `String`」拷貝問題：

- 從 `Data` / `[UInt8]` 建立 `String`（如 `String(decoding:as: UTF8.self)`）一定會做一次 copy，把 bytes 搬進 `String` 的內部儲存；在 Darwin 上若走 `Foundation` 橋接，還可能產生 `NSString` 包裝。
- 若先將整塊 raw `Data` 物化為一個巨大 `String`，再往後只回傳 `Substring`，雖能共享儲存，但會改變 public API（`String` → `Substring`），且 `Substring` 轉回 `String` 時仍會觸發 copy。
- 目前 `TrieTextMap_Core` 已在關鍵路徑使用 byte-level 掃描（`compareUTF8Buffers`、`initialsUTF8: ContiguousArray<UInt8>`、`collectReverseLookupCharsFromLine` 等），這實際上已經達到 `utf8View` 的精神：比對、索引、反查建構都在 bytes 層完成，只在回傳給 caller 時才建立 `String`。

因此，在維持現有 `String`/`[String]` 介面的前提下，無法再進一步讓回傳的 `String` 零拷貝指向 raw `Data` 區段；`TrieStringPool` 的 intern + LRU eviction（方向 6）已是這條界線內最務實的壓縮手段。

6. **Wildcard 前綴掃描熱徑 byte-length 判斷**：`wildcardValuesFor` 在掃描匹配 key 時，原實作會把每個 key 解碼成 `String` 後以 `count` 判斷是否嚴格大於前綴長度。由於 CIN `chardef` 字根鍵皆為 ASCII，byte count 等同 `Character` count，因此改為直接比較 `keyEnd - keyStart > prefixUTF8.count`，避免在熱迴圈內重複進行 UTF-8 解碼與 `String` 配置。

### Wildcard 查詢效能理論估算

移除獨立 `charDefWildcardMap` 後，wildcard 查詢改為對 `charDefMap` 做 lower-bound binary search 加上前綴線性掃描。原始 map 是 exact-match binary search（`O(log W)`，W 為 wildcard 專屬 entry 數）；新做法的複雜度主要取決於「與前綴共享的字根鍵數量」。

以常見 CIN 為例：

| CIN | 總 key 數 | 單一字首平均共享 key 數 | 兩字首平均共享 key 數 | 三字首平均共享 key 數 |
|-----|----------|------------------------|----------------------|----------------------|
| 五筆 86 | ~23,000 | ~900 | ~34 | ~1.3 |
| 行列 30 | ~29,000 | ~740 | ~18 | ~0.5 |

- 對於 `a?` 這類單一字首萬用字元查詢，掃描量約數百個 key；兩字首以上則通常只剩個位數或數十個。
- 經 byte-length 最佳化後，熱迴圈內不再需要將每個 key 解碼為 `String`，每個 key 的成本為幾次 byte 比較與一次 `valueString(at:)` 取值（僅對符合條件的 key）。
- 現代 Apple Silicon 處理數百次迭代只需數微秒等級；對於日常打字路徑（`hasUnigramsFor` → wildcard）理論上幾乎無感。若未來在 Instruments 中觀察到明顯延遲，可再考慮加入前綴共享 key 數快取或將 wildcard 結果快取成小型 LRU。

> 以上估算的前提是 CIN `chardef` 字根鍵仍維持 ASCII。若將來出現非 ASCII 字根鍵，byte-length 捷徑即不成立，需改回 `String(decoding:).count` 判斷。

### 調查結論：全量複製的來源

現行 `LMCassette.open()`（`lmCassette.swift` L1036-1040）在建置 `charDefMap` / `symbolDefMap` 之後，緊接著以 `buildReverseLookup(charDefs:symbolDefs:)`（L634-703）自暫存 Dictionary 生成 `reverseLookupMap`。該函式把「全部反查 key（字詞）＋ 全部反查 value（碼）」重新複製進第三份 `rawData`，再另建自己的 entries 與 valueOffsets。

關鍵事實：**反查表的 key 與 value 的 bytes 本來就都已經存在於 `charDefMap` / `symbolDefMap` 的 `rawData` 內**（字詞 = charDef/symbolDef 的 value 範圍；碼 = 其 key 範圍）。因此全量複製可以完全避免，無需退而求其次做 lazy load。

|---|---|---|
| `revChars: [UInt8]` | 僅去重後的唯一字詞 bytes（唯一被複製的部分） | ~30KB（~1 萬字 × 2~3B） |
| `revEntries: [CassetteReverseEntry]` | `(charStart, charEnd, refsStart, refsEnd)` 16B × 唯一字數 | ~160KB |
| `revCodeRefs: [UInt32]` | 每筆記錄 4B，指向 charDef/symbolDef 的合併 entry index | ~200KB（5 萬筆時） |

- 碼字串完全不複製：查詢時依 refs 讀取來源 map 的 `entry.keyStart..<keyEnd`，按需物化。
- charDef 與 symbolDef 以合併 namespace 處理（charDef entries 在前、symbolDef 以 offset 接續），保留現行「兩者合併反查」語義。
- ⚠️（Kimi 修訂）**建置時必須涵蓋 charDefMap 的全部 entries，含花牌 pattern keys**：Phase 128 起 `charDefWildcardMap` 已刪除、花牌 entries 混存於 `charDefMap`，而現行 `buildReverseLookup` 自暫存 Dictionary 建置時亦包含它們；漏收會造成「反查結果不列 pattern 碼」的語義偏差。
- ⚠️（Kimi 修訂）**同字詞多碼的組內順序改為確定性**：現行 `buildReverseLookup` 使用非穩定 `sort`，同 lookupKey 的碼排列本就未定義；新索引改以 ref 升冪（charDef 先、各依碼 bytes 序）。`cassetteReverseLookup` 後處理的兩次 stableSort 若遇完全平手（同碼長、同 unigram 數），最終顯示順序可能與舊 build 不同——屬可接受的行為漂移，記錄於此。
- 建置順序調整：`open()` 先建 `charDefMap` / `symbolDefMap`，再掃二者 entries + valueOffsets 生成反查索引；`buildReverseLookup` 現有的 `[Prototype]`（String 對）暫存陣列可一併移除，略降建置峰值。

### 行為保留契約（不得破壞）

- `cassetteReverseLookup(for:)` 的後處理（trim newlines → 依碼長 stableSort → 依 unigram 數 stableSort）與「無結果回傳 `[]`」語義不變。
- 反查 key 為 charDef/symbolDef 的 value（單字或字詞皆可）；結果為碼（來源 map 的 key range，按需物化）。
- symbolDef 合併語義保留（合併 namespace：charDef entries 在前、symbolDef 以 offset 接續）。
- Phase 129 的 wildcard / anagram 機制（`patternValuesFor` / `containsPatternMatch` / `hasCassetteWildcardResultsFor`）完全不受影響——手術僅更換 `reverseLookupMap` 一個欄位。
- `open()` 建置順序：先 `charDefMap` / `symbolDefMap`、再反查索引；`tmpCharDef` / `tmpSymbolDef` 在兩個 map 建完後立即 `removeAll(keepingCapacity: false)` 釋放，略降載入期峰值。
- 純 Swift `[UInt8]` / `[UInt32]` 實作，無新平台依賴（macOS 10.9 / Linux / Windows 相容性不變），不碰 NS 開頭類型。

### 記憶體與延遲估算

| | 現況（Array30 量級粗估） | 零複製版 |
|---|---|---|
| 反查索引常駐 | 複製 blob ~200KB + entries ~190KB + valueOffsets ~400KB ≈ 0.8MB（大型 CIN 可達 2~4MB） | ~0.4MB |
| 查詢延遲 | 二分搜尋大 blob + 物化 | 二分搜尋更小的單一連續 blob + 按需物化，更快 |

- **不做 lazy load**：維持 eager 建置（注音模式選字窗內的字根反查不容半點延遲），本設計不需要 lazy 即可達成減量。
- 查詢路徑唯一消費端為 `cassetteReverseLookup(for:)`（`LMInstantiator_CassetteExtension.swift`，兩倉庫各一處），API 面可完全相容；`clear()` 重置新增兩欄即可。

### 已知邊界（誠實提醒）

反查表僅為「1.3MB CIN → ~12MB 佔用」的部分來源（結構常駐粗估 ~3.5MB 上下）。其餘疑為 `open()` 期間暫存 Dictionary 與最終結構並存造成的載入期峰值：malloc 釋放後不會立刻還給 OS，以 dirty pages 殘留、待系統回收（與「不打字幾秒後跌回」的觀察相符）。若後續仍需減量，屬 Phase 128 選項清單中未實作的「載入期峰值降低」。

## Phase 130 實作結果（2026-08-01，macOS Repo & Legacy Repo）

### 零複製反查索引落地

- 新增 `CassetteReverseEntry`（16B）與 `CassetteReverseIndex`（`revChars` 去重字詞 bytes + `revEntries` + `revCodeRefs` 合併 namespace entry 索引 + `charDefEntryCount`）。建置掃描 `charDefMap` / `symbolDefMap` 全部 entries × values（**含花牌 pattern keys**，與舊版自暫存辭典建置等價），依 value bytes 排序、同 value 依 ref 升冪（確定性順序），去重後分組。
- 新增 `LMCassette.reverseCodes(for:)`：二分搜尋 `revChars` 命中後，依 refs 自來源 map 的 `rawData[keyStart..<keyEnd]` 按需物化碼字串。`cassetteReverseLookup(for:)` 僅改接此 API，後處理（trim newlines → 碼長 stableSort → unigram 數 stableSort）未動。
- 移除 `reverseLookupMap: CassetteSortedMap` 欄位與 `buildReverseLookup`（第三份全量複製 blob 消除）；`open()` 於全部 map 建完後即刻 `removeAll(keepingCapacity: false)` 釋放六個暫存 Dictionary。
- 新增 `[UInt8].cassetteCompareUTF8Slices` 雙 slice 字典序比較 helper（排序與去重共用，避免物化 String）。

### 差分驗證（三步程序）

1. 第一階段新舊並存：`open()` 同時建置 `reverseLookupMap` 與 `reverseIndex`。
2. 臨時差分測試：以 array30.cin2（29,491 chardef keys + symboldef）與 wubi.cin（23,494 keys）對新索引列舉出的**每一個反查字詞**逐一比對新舊查詢結果（集合語義）＋唯一字詞數相等＋不存在的字詞雙雙 nil——全數一致（約 5.1 秒跑完）。
